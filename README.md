# store-connect

The Store Systems edge service that sits between a store's point of sale, the commerce API and the kitchen. Three modules, one process, one port:

| Module        | Does                                                                        | Entry              |
| ------------- | --------------------------------------------------------------------------- | ------------------ |
| `pos-adapter` | turns POS order events into commerce API calls, with a stub POS for laptops | `src/pos-adapter/` |
| `kds-feed`    | a Socket.IO feed of kitchen tickets, one room per store                     | `src/kds-feed/`    |
| `throttle`    | per-store order throttling with a token bucket, in memory or in Redis       | `src/throttle/`    |

Plus `/health`, `/ready` and `/metrics` (`src/health.ts`, `src/metrics.ts`), structured JSON logs (`src/logging.ts`) and OpenTelemetry tracing with a correlation id on every outbound call (`src/telemetry.ts`, `src/correlation.ts`).

## Run it

One command from a fresh clone:

```bash
npm run setup      # installs dependencies, writes .env from .env.example, checks the toolchain
npm run dev        # memory throttle store, stub POS emitting orders every 4 seconds, port 8080
```

With Redis, the way the fleet runs it:

```bash
docker compose up  # the service plus Redis; /ready goes green once Redis answers
```

Then:

```bash
curl -s localhost:8080/health
curl -s localhost:8080/ready
curl -s localhost:8080/metrics | grep store_connect_
curl -s localhost:8080/throttle/101
```

A kitchen display connects to `ws://localhost:8080/kds`, emits `subscribe` with its store id and receives `ticket` events. `docs/architecture.md` has the sequence; `docs/openapi.yaml` describes the HTTP routes.

## Develop

```bash
npm test                 # unit tests and the KDS feed integration test (vitest)
npm run test:coverage    # the same with coverage
npm run lint             # eslint
npm run format:check     # prettier (npm run format fixes)
npm run typecheck        # tsc, no emit
npm run build            # dist/ for the container image
```

The devcontainer (`.devcontainer/devcontainer.json`) runs `npm run setup` on create and starts Redis on open.

## CI

`.github/workflows/ci.yml` runs on every change and on `main`: install from the lock, compile, type check, lint, format check, tests with coverage, and `npm audit` at level high. The job token is read-only.

`.github/workflows/ci-template.yml` is the same pipeline as a reusable workflow. The other Store Systems TypeScript repositories call it with `uses: wwtdigital/copperpot-store-connect/.github/workflows/ci-template.yml@main`; a change to the steps is made in `ci.yml` first so it runs here before anyone else picks it up.

## Release and promotion

Releases are tags. A tag is promoted to the stores in three stages (pilot, region, all), each a cohort behind a health gate, defined in `infra/` and planned by `.github/workflows/deploy-promote.yml`; the apply runs from the fleet operator's console. `docs/release.md` is the procedure, including rollback (`scripts/rollback.sh`).

## Operations

`docs/runbooks/` has one runbook per paging alert: [stalled KDS feed](docs/runbooks/stalled-kds-feed.md), [throttle misfire](docs/runbooks/throttle-misfire.md), [POS adapter backlog](docs/runbooks/pos-adapter-backlog.md). The index lists what fires each alert and where to look. `SECURITY.md` has the reporting address and the triage service levels.

Coverage is gated at 70 (`vitest.config.ts`); a change that drops under it fails the pipeline.

## Environment variables

Every variable the service reads is listed in `.env.example` with its default and a comment; `npm run setup` copies it to `.env`. The ones that matter in a store:

| Variable                                          | Default                       | Why                                                                                  |
| ------------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------ |
| `THROTTLE_STORE`                                  | `memory`                      | `redis` on the fleet edge, where two instances front the same stores                 |
| `THROTTLE_CAPACITY`, `THROTTLE_REFILL_PER_MINUTE` | `20`, `12`                    | the default bucket per store                                                         |
| `THROTTLE_OVERRIDES`                              | empty                         | `storeId:capacity:refillPerMinute,...` for stores with one grill                     |
| `COMMERCE_API_URL`                                | `http://localhost:4100/store` | the store application of the commerce API                                            |
| `POS_MODE`                                        | `stub`                        | `feed` in a store; the stub emits synthetic orders                                   |
| `SERVICE_VERSION`                                 | `local`                       | set to the release tag by the promotion tooling; shows in logs, `/health` and traces |
| `OTEL_EXPORTER_OTLP_ENDPOINT`                     | `http://localhost:4318`       | empty disables tracing                                                               |

## Logs, traces, metrics

- Logs are JSON lines with `service`, `version` and `level` on every line, `requestId` on HTTP lines, `correlationId` on everything the adapter does for one POS order.
- The correlation id travels as `x-correlation-id` on the call to the commerce API and on the kitchen ticket, with the W3C `traceparent` beside it when tracing is on.
- `/metrics` exposes `store_connect_pos_events_total{type,outcome}`, `store_connect_throttled_orders_total{store}`, `store_connect_kds_tickets_total{store}` and `store_connect_commerce_request_seconds{outcome}`, plus the Node process defaults.
